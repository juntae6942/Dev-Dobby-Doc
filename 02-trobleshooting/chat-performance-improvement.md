# 채팅 성능 개선 실험 보고서

## 요약

채팅 메시지를 보낼 때 두 참여자의 채팅방 목록을 갱신하는 경로에서 반복 조회를 줄였다. 조회 최적화 전 로컬 실험에는 250소켓에서 p95 147ms~3.74초까지 넓은 편차가 있었다. 쿼리 최적화 직전 275소켓 실행의 p95는 80ms였고, 변경 후 275소켓 세 실행은 p95 18~66ms였다. 이 80ms는 앞선 250소켓 결과를 대표하는 값이 아니라, 최적화 전후 275소켓 비교에 사용한 직전 실행이다. 변경 후 세 번 모두 메시지 전달률 100%, STOMP 오류 0건이었다.

실험은 **dev 서버**와 **개발자 로컬 서버**에서 나누어 진행했다. dev 서버에서는 연결 수와 전달 동작을 확인했고, 서버 내부 Timer 계측 및 코드 최적화 전후 측정은 로컬에서 진행했다. 두 환경의 수치는 직접 비교하지 않는다. 변경 전 실행이 한 번뿐이고 동일 부하에서도 결과 편차가 있었으므로, 로컬 최적화 결과를 운영 환경의 처리 한계나 확정적인 개선율로 해석하지 않는다.

## 환경별 범위

| 구분 | 대상과 확인 방법 | 이 보고서에 포함한 결과 |
|---|---|---|
| dev 서버 | 기본 BASE_URL인 `https://dev.gachigacha.kro.kr/api/v1` 사용. 실행 시 서버 주소를 따로 지정하지 않은 테스트 | 채팅방 데이터 준비, 50/100/200개 소켓 연결 및 500개 연결 확인, 초기 메시지 전달·drain 시험 |
| 로컬 서버 | `BASE_URL=http://localhost:8080/api/v1` 명시 | 5소켓 메시지 smoke, 단계별 Timer 및 STOMP 큐 대기 계측, 200~275소켓 메시지 latency 실험, 조회 최적화 전후 비교 |

두 환경은 별도 실행으로 기록하며 결과를 합산하거나 직접 비교하지 않는다. 초기 기록에서 명령이나 BASE_URL이 보존되지 않은 수치는 본문에서 대상 미확인으로 표시한다.

### 로컬 메시지 부하 시험 공통 설정

- URL: `http://localhost:8080/api/v1`
- 도구: k6 `chat-message-latency.js`, refresh token pair 실행기
- 인증: 채팅 요청자 계정 (`TOKEN_INDEX=2`)
- 데이터: 각 VU가 서로 다른 기존 채팅방 하나에 연결
- 대표 부하: 소켓별 1초 간격, 60초 송신, 연결 후 15초 대기, 첫 전송 최대 15초 분산, drain 15초
- STOMP 인바운드·아웃바운드 실행기: core 32 / max 64 / queue 100
- 지표: 메시지 전달률, 왕복 지연 p95, STOMP 오류, inbound/outbound 큐 대기 시간

## 단계별 계측과 개선 결정 과정

아래는 dev 서버 연결 확인에서 시작해 로컬 계측과 최적화 검증으로 이어지는 시간순 기록이다. 수치는 사용자가 각 실행에서 공유한 결과를 옮겼다. 로컬 서버의 Timer는 재시작 전까지 누적되는 경우가 있었으므로, 누적 카운터 차이를 구한 값과 단일 실행의 k6 결과를 구분한다.

### 1. 테스트 데이터 준비와 dev 서버 연결 수 확인

dev 서버 부하 준비에는 같은 계정이 작성한 교환 게시글 ID 74~84947 중 일부를 활용했다. 게시글 작성자와 채팅 요청자 refresh token을 별도로 사용했고, refresh token은 갱신 후 재사용할 수 없어 `already used` 응답이 나면 해당 계정에 다시 로그인해 새 토큰을 발급했다. 요청자 member 45 기준으로 채팅방 ID 74~573이 생성된 것을 확인했다. 이후 dev 연결 테스트에서는 준비된 서로 다른 방을 사용했다.

dev 서버 연결 전용 시험은 50, 100, 200개에서 시작했고 handshake와 STOMP `CONNECTED`가 성공하며 STOMP 오류가 0건이었다. 첫 스크립트 실행에서는 소켓을 60초 유지하는 동안 iteration 제한 시간이 먼저 끝나 `setInterval ... interrupted`, `No script iterations fully finished` 경고가 났다. 이어 실행 시간을 늘렸을 때는 iteration 완료 경고가 남았고, 다른 실행에서는 STOMP `Session closed` 및 WebSocket close 1002 오류가 발생했다. 이 중간 결과는 단순한 정상 종료 경고만은 아니며, 일부 세션이 실제로 종료된 문제도 포함했다.

이후 스크립트와 세션 종료 처리를 보완하고 다시 연결 수를 늘려, dev 서버에서 500개 소켓이 연결되는 것을 확인했다. 따라서 500개 연결 확인은 위 중간 실행의 경고와 별개인 후속 결과다. 다만 공유된 최종 기록은 연결 수 확인에 관한 것이므로, 이 결과만으로 500개 연결의 장시간 유지나 해당 연결 상태에서의 메시지 처리량까지 검증됐다고 보지는 않는다. 메시지 전송 부하 시험과 서버 내부 계측은 아래에 별도 환경과 결과로 기록한다.

### 2. 소켓·메시지 스모크 테스트

로컬 서버에서 처음 메시지 시험은 5개 소켓, 30초 연결 유지, 소켓별 3초 간격으로 진행했다. 45건을 보내 45건을 받았고, 전달률 100%, STOMP 오류 0건, 지연 p95 35.39ms였다. 같은 설정의 반복에서도 45/45 메시지 전달, p95 32.59ms, STOMP 오류 0건이 나왔다. 이는 로컬 `/ws` 동작 확인이지 dev 서버 결과나 서버 수용량 측정은 아니다.

### 3. 로컬 서버 처리 단계별 Timer 추가

클라이언트의 왕복 지연만으로 병목 위치를 알기 어려워 `chat.message.stage` Timer를 임시로 추가했다. 계측은 다음 순서로 넓혔다.

1. 메시지 검증, 채팅방 잠금·조회, 참여자/정책 검사, Mongo 저장, DB 업데이트·이벤트 발행
2. 서비스 전체, STOMP topic broadcast, 채팅방 목록 갱신
3. 채팅방 갱신 내부의 방·멤버십·상대·게시글·썸네일 조회, 전체 안 읽은 수, 차단 검사
4. 클라이언트 인바운드·아웃바운드 STOMP 채널의 executor 대기 시간

로컬 5소켓 스모크 테스트와 초기 저부하 계측 구간에서 관측한 대표 Timer 스냅샷은 다음과 같다.

| 초기 Timer 구간 | 횟수 | 총 시간 | 평균 |
|---|---:|---:|---:|
| Mongo 메시지 저장 | 51 | 451.6ms | 8.86ms |
| Topic broadcast | 51 | 54.8ms | 1.07ms |
| 채팅방 목록 갱신 전체 | 51 | 1.139초 | 22.33ms |
| 목록 갱신의 참여자별 작업 | 90 | 796.7ms | 8.85ms |
| 참여자 ID 조회 | 45 | 92.6ms | 2.06ms |

추가 조회별 스냅샷에서는 개별 room/member/partner/trade/thumbnail/block/unread Timer 평균이 대체로 0.8~1.5ms였고, 전체 안 읽은 수 조회는 별도 실행에서 약 1.3~1.4ms였다. 이 값들은 모두 한 번의 깨끗한 실행에서 동시에 뽑은 표가 아니다. 서버를 재시작하지 않은 구간은 COUNT와 TOTAL_TIME이 누적될 수 있어, 평균은 각 Timer의 `TOTAL_TIME / COUNT`로 해석하고 서로 다른 스냅샷 값을 더해 전체 요청 시간을 계산하지 않았다.

저부하에서는 특정 개별 DB 조회 하나가 지배적이라고 보기 어려웠다. 대신 메시지마다 참여자 둘의 목록 갱신을 동기 처리하는 코드 경로가 반복 작업의 후보로 드러났다.

### 4. dev 서버 메시지 drain 시험과 로컬 STOMP 채널 대기 계측

dev 서버의 초기 메시지 시험에서는 메시지 전송 간격을 3초, 2초, 1초로 줄이고 drain을 5초, 60초, 120초로 바꿔 전달을 확인했다. 1초 간격에서는 60초 drain 때 약 22~24%만 도착한 실행이 두 번 있었지만, 120초 drain에서는 29,692건 중 29,692건이 돌아왔다. 이 결과로 메시지가 유실됐다고 단정했던 초기 해석을 수정했다. 대기 시간을 늘리면 전달률은 회복했지만 실시간 채팅 기준으로는 충분하지 않으므로, 로컬 측정 단계에서 메시지 본문에 넣은 송신 timestamp와 수신 시각 차이를 기록하는 latency Trend를 추가하고 p95 1초 기준을 설정했다.

로컬 서버에서는 5소켓 smoke에서 250소켓, 1초 간격, 60초 송신 구간으로 확장했다. 250 VU는 14,750건을 송신해 모두 수신하고 STOMP 오류는 0건이었지만, 지연 p95는 실행마다 895ms, 3.74초, 3.67초 등으로 크게 달랐다. 첫 메시지 구간에서 수 초 지연이 나고 뒤 구간은 낮은 지연을 보이는 결과도 있어, 메시지 유실 여부와 별개로 서버 내부 대기 위치를 찾아야 했다.

서비스 내부 Timer만으로 수 초 지연이 설명되지 않아 STOMP inbound/outbound executor queue wait Timer를 추가했다. 한 누적 스냅샷에서는 inbound COUNT 44,250, TOTAL_TIME 16,666.43초, MAX 2.238초가 관측됐다. 이 스냅샷의 누적 평균은 약 377ms/측정 이벤트지만 여러 실행이 합쳐진 값이므로 특정 k6 실행의 평균으로 사용하지 않았다. 이로써 채널 대기에서 초 단위 지연이 생길 수 있음을 확인했다. 이후 측정 도구의 handler 필터를 조정해 inbound는 메시지 핸들러, outbound는 WebSocket 전송 핸들러에서만 계측하도록 보정했다.

같은 조건을 재실행한 결과도 달랐다. 예를 들어 p95 623ms 실행에서는 inbound/outbound 평균 대기가 각각 약 29.5ms/29.7ms였지만, 서버를 재시작하지 않은 다음 실행에서 p95가 2.13초와 1.69초로 올라갔다. 누적 Timer의 COUNT/TOTAL_TIME 차이로 계산한 해당 실행 평균은 inbound/outbound 합계 약 242ms와 194ms였다. Hikari 지표는 일부 관찰 구간에서 pending 0, active 최대 9/10이었지만, 테스트 종료 뒤의 active=0/pending=0 값은 실행 중 DB 대기 여부를 설명하지 않는다.

병목 탐색은 단계 타이머, Hikari 지표, 클라이언트 지연을 같은 테스트 시간대에 맞춰 보는 방식으로 진행했다. `service`/`room_updates`의 누적 시간과 `room_update_*` 세부 Timer를 비교해 조회 및 목록 갱신 경로에 집중했고, Hikari pending이 0이라는 사실만으로 DB가 병목이 아니라고 결론 내리지 않았다. 특히 첫 메시지 구간에서만 지연이 치솟는 실행이 반복되어 연결 직후 메시지 집중이 결과를 왜곡하는지 분리할 필요가 있었다.

### 5. 로컬 STOMP inbound/outbound 실행기 설정

채널 작업자 수와 큐 크기를 실험에서 제어할 수 있도록 inbound/outbound 실행기를 분리 설정했다. 기본값은 각각 core 32 / max 64 / queue 100이며, 앞 절의 환경 변수로 조정 가능하다. 이 설정을 적용한 뒤에도 같은 250소켓 실행의 지연이 반복마다 달랐으므로 실행기 설정만으로 일관된 개선이 확인됐다고 보기는 어려웠다.

이후 로컬 테스트 스크립트에 STOMP 연결 뒤 15초 대기와 VU별 최대 15초의 첫 전송 분산을 넣었다. 대기만 적용한 첫 명령은 스크립트가 해당 변수를 읽지 않아 실제로는 적용되지 않았고, 옵션을 구현한 뒤 다시 측정했다. 전송 시작을 분산한 로컬 250소켓 실행의 p95는 970ms, 147ms, 551ms로 달랐다. 로컬 200소켓 실행은 p95 16ms였고, 로컬 225소켓은 두 실행에서 30ms와 346ms였다. 이 변동 때문에 특정 소켓 수를 고정 한계로 결론 내리지 않고, 반복 결과와 서버 내부 계측을 함께 보도록 했다.

STOMP 설정 전후는 설정 파일 변경 자체의 효과를 분리한 통제 실험이 아니다. 실행기 분리·환경변수화와 큐 대기 계측을 도입해 실험 가능성을 높였지만, 같은 조건에서 설정만 바꾼 반복 A/B 데이터는 남아 있지 않다. 따라서 이 보고서에서는 해당 설정이 개선을 만들었다고 주장하지 않고, 그 뒤 조회 쿼리 통합 전후의 결과를 별도로 비교한다.

### 6. 로컬 코드 경로 최적화로 이어진 판단

로컬 계측 결과를 종합해 executor 크기를 계속 키우기보다, 메시지마다 두 참여자에게 동기 전송하는 채팅방 목록 갱신의 반복 DB 조회를 먼저 줄이기로 했다. 최적화 전 로컬 250소켓 시험에서는 p95가 크게 흔들렸다. 첫 메시지 구간이 특히 높았던 실행도 있었고, 첫 전송 분산을 적용한 실행에서도 수치 편차가 남았다. 최적화 직전의 별도 275소켓 실행은 평균 22.79ms, p95 80ms였다. 이는 250소켓 이전 결과와 부하·전송 시작 조건이 완전히 같지 않으므로 대표적인 단일 기준값으로 섞지 않는다. projection 조회 통합 후 로컬 275소켓 세 실행은 p95 18ms, 66ms, 21ms였고 세 실행 모두 전달률 100%, STOMP 오류 0건이었다. 비교 실행의 수치와 조건 차이는 아래 표에서 나누어 제시한다.

## 로컬 조회 최적화 전후 결과

### 조회 최적화 전 로컬 지연 실험 이력

아래는 조회 최적화 전에 수행한 1초 간격·60초 송신 구간의 로컬 메시지 시험 결과다. 250소켓 실행끼리도 첫 전송 대기·분산 설정과 실행 시점이 달라 결과가 흔들렸다. 전체 이력은 병목을 발견하게 된 근거이며, 최적화 전후 효과를 단독으로 판정하는 통제 비교표는 아니다.

| 실행 조건/단계 | 소켓 | p95 지연 | 메모 |
|---|---:|---:|---|
| 초기 부하, 전송 시작 분산 전 | 250 | 895ms | 전달률 100%, STOMP 오류 0건 |

## 코드 변경

### 로컬 코드 변경: 채팅방 갱신 조회 통합

기존 메시지 처리 경로에서 참여자 ID를 가져오는 조회는 방마다 1회였다. 그 뒤 참여자 한 명마다 다음 7개 조회가 발생했다.

| 참여자 한 명당 기존 조회 | 횟수 |
|---|---:|
| 채팅방 | 1 |
| 내 멤버십 | 1 |
| 상대 회원 | 1 |
| 게시글 | 1 |
| 썸네일 | 1 |
| 전체 안 읽은 수 | 1 |
| 차단 여부 | 1 |
| **소계** | **7** |

따라서 정상적인 1:1 방에서 예상한 합계는 `참여자 ID 1 + 참여자 2명 × 조회 7 = 15`회다.

`ChatRoomUpdateProjection`과 `ChatRoomJpaRepository.findRoomUpdate`를 추가해 방·상대·게시글·썸네일·방별 안 읽은 수·차단 여부를 참여자당 projection 조회 1회로 합쳤다. 썸네일 선택 서브쿼리와 차단 `EXISTS`는 projection SQL 안에서 실행되므로 별도 DB 왕복으로 세지 않는다. 전체 안 읽은 수는 기존 `countUnreadMessage` 경로를 재사용해 참여자당 1회 별도로 조회한다.

변경 후 정상적인 1:1 방 기준 예상 합계는 `참여자 ID 1 + 참여자 2명 × (projection 1 + 전체 안 읽은 수 1) = 5`회다. 즉 예상 조회 수는 15회에서 5회로 줄었다. 차단된 경우 전체 안 읽은 수 조회는 생략된다. 방·멤버십·상대·게시글이 없는 예외 경로의 검증 조회는 이 정상 경로 계산에 포함하지 않았다.

**횟수의 기준은 메시지 한 건이 처리되어 두 참여자의 채팅방 목록 갱신 이벤트를 만드는 정상 1:1 방 한 개**다. 15회와 5회는 repository 호출이 수행되는 횟수의 코드 경로 추산이다. 하나의 projection 쿼리 안에 들어간 썸네일 서브쿼리나 차단 `EXISTS`는 애플리케이션과 DB 사이의 별도 왕복으로 세지 않는다. 전체 안 읽은 수 계산은 참여자별 기존 쿼리를 재사용하므로 projection 쿼리에 포함되지 않는다. 따라서 “조회 수 3분의 1”은 논리적 조회 왕복 추산에 관한 설명이며, 전체 CPU/DB 실행량이 같은 비율로 줄었다는 뜻은 아니다.

이 값은 현재 코드 흐름의 repository 조회 횟수를 기준으로 한 추산이다. ORM 캐시, 실행 계획, 데이터베이스 내부의 서브쿼리 실행량까지 측정한 절대 SQL 횟수는 아니다.

### 응답 매핑과 예외 동작

- `ChatRoomInfo.of`로 탈퇴 회원 표시와 게시글 상태 변환을 모았다.
- 차단된 방만 갱신 대상에서 제외한다.
- 방, 멤버십, 상대 회원 또는 게시글이 없는 경우 기존 예외 동작을 유지하도록 조회 결과를 검증한다.
- `member_block`에는 soft delete 조건이 없어 native query의 차단 검사가 기존 차단 조회와 같은 방향·역방향 조건을 사용한다.

### 채널 실행기와 측정 코드

인바운드와 아웃바운드 STOMP 채널은 서로 독립된 실행기를 사용한다. 각 설정은 `application.yaml`에서 환경 변수로 덮어쓸 수 있다.

| 채널 | Core threads | Max threads | Queue capacity | 환경 변수 |
|---|---:|---:|---:|---|
| Inbound | 32 | 64 | 100 | `CHAT_WS_INBOUND_CORE_POOL_SIZE`, `CHAT_WS_INBOUND_MAX_POOL_SIZE`, `CHAT_WS_INBOUND_QUEUE_CAPACITY` |
| Outbound | 32 | 64 | 100 | `CHAT_WS_OUTBOUND_CORE_POOL_SIZE`, `CHAT_WS_OUTBOUND_MAX_POOL_SIZE`, `CHAT_WS_OUTBOUND_QUEUE_CAPACITY` |

설정 예시는 다음과 같다. 환경 변수를 지정하지 않은 로컬 실험에서는 이 기본값을 사용했다.

```yaml
chat:
  websocket:
    inbound:
      core-pool-size: ${CHAT_WS_INBOUND_CORE_POOL_SIZE:32}
      max-pool-size: ${CHAT_WS_INBOUND_MAX_POOL_SIZE:64}
      queue-capacity: ${CHAT_WS_INBOUND_QUEUE_CAPACITY:100}
    outbound:
      core-pool-size: ${CHAT_WS_OUTBOUND_CORE_POOL_SIZE:32}
      max-pool-size: ${CHAT_WS_OUTBOUND_MAX_POOL_SIZE:64}
      queue-capacity: ${CHAT_WS_OUTBOUND_QUEUE_CAPACITY:100}
```

`core-pool-size`는 기본 worker 수, `max-pool-size`는 큐가 포화된 뒤 늘어날 수 있는 상한, `queue-capacity`는 worker가 바쁠 때 대기할 작업 수다. 따라서 max 64는 항상 64개 스레드가 동작한다는 의미가 아니다. 이 실험에서는 실행기 값은 고정하고 조회 경로를 개선했다.

성능 분석을 위해 추가했던 `chat.message.stage` 단계 타이머와 STOMP 큐 타이밍 인터셉터는 실험 후 제거했다. HTTP·S3 등 기존 메트릭은 유지했다.

## 해석과 한계

- 변경 후 275소켓 세 번 모두 p95가 66ms 이하였다. 이번 로컬 조건에서는 메시지 왕복 지연과 전달 안정성이 개선된 결과다.
- 변경 전 비교값은 단일 실행이고 변경 후는 세 번 실행이라 통계적으로 통제된 A/B 실험은 아니다. 같은 소켓 수에서도 과거 결과 편차가 컸다.
- k6와 백엔드가 같은 개발자 컴퓨터에서 실행되어 CPU·GC·백그라운드 작업 영향을 분리하지 못했다.
- 테스트 후 Hikari active/pending은 0이었지만, 테스트 중 최대 사용량을 나타내지 않는다.
- 따라서 “275개 소켓에서 이 로컬 실행 조건으로 통과했다”는 결론은 가능하지만 운영 환경의 최대 수용량으로 일반화할 수 없다.
- 상세 성능 타이머는 제거했으므로 현재 서버에서 `chat.message.stage` 지표를 더는 조회할 수 없다.
